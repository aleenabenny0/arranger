# Security

This document lists the controls that exist, the test that pins each one, and
what is known to be missing. It does not claim the application is free of
vulnerabilities. Nobody outside the project has reviewed or penetration-tested
it.

Operational procedures (rotation, incident response, backups) are in
`docs/runbook.md`.

## Controls and where they are tested

### Accounts and sessions

| Control | Tested in |
|---|---|
| Passwords hashed with Argon2id. Older PBKDF2 hashes still verify and are upgraded to Argon2id on the next successful sign-in. | `tests/test_api_auth.py`, `tests/test_security.py` |
| Sign-in takes the same path and time for an unknown address as for a wrong password. Registration, reset and resend never reveal whether an address has an account. | `tests/test_api_auth.py` |
| Session tokens are random, stored only as hashes, expire absolutely (`SESSION_DAYS`) and when idle (`SESSION_IDLE_DAYS`), and are capped per user. A password change or reset revokes every other session. Users can list and revoke sessions. | `tests/test_api_auth.py` |
| Session cookie is `HttpOnly`, `SameSite=Lax`, and `Secure` in production. | `tests/test_api_auth.py`, `tests/test_settings.py` |
| CSRF: a token bound to the session (not a free-standing double-submit cookie) is required on every state-changing request, together with an `Origin` that is on the allow-list. | `tests/test_api_auth.py`, `tests/test_api_projects.py` |
| Reset and verification tokens are single-use, time-limited, stored as hashes, and consumed atomically: six concurrent confirmations produce exactly one success (also run against real Postgres). | `tests/test_api_auth.py`, `tests/test_postgres_integration.py` |
| Emailed links carry the token in the URL fragment, which browsers never send to a server; the app removes it from the address bar on arrival; `Referrer-Policy: no-referrer`. | `tests/test_email.py`, `tests/test_browser_e2e.py` |
| Email verification is required before uploading or arranging when `REQUIRE_VERIFIED_EMAIL` is on (the production default). | `tests/test_api_auth.py`, `tests/test_browser_e2e.py` |

### Authorisation

| Control | Tested in |
|---|---|
| Every project, source, arrangement, job and artifact query is scoped by user id inside the repository layer, not in the route. Another user's id returns 404, never 403, so existence is not revealed. Twenty cross-user probes are asserted. | `tests/test_api_projects.py`, `tests/test_api.py` |
| A source from one project cannot be used to arrange in another. | `tests/test_api_projects.py` |
| Storage keys are generated by the server; every store refuses a key with traversal, separators or NUL in it, and download filenames are stripped of quotes, newlines and path characters. | `tests/test_artifacts.py` |
| Downloads are authorised against the database and streamed by the API. Storage keys and bucket URLs never reach a browser. Downloads are `Content-Disposition: attachment`, `nosniff`, `no-store`, with a sanitised filename. | `tests/test_api_projects.py` |

### Untrusted input

| Control | Tested in |
|---|---|
| Body size is enforced while streaming, not only from `Content-Length`; chunked bodies, lying lengths and malformed lengths are refused. Upload routes have their own larger cap. | `tests/test_api_security.py` |
| Every numeric field in scores, plans and profiles is bounded (pitch, time, bar, tempo, list lengths, text lengths). Unknown fields are rejected. | `tests/test_api_security.py`, `tests/test_agent.py` |
| MIDI parser: hand-written, bounds-checked, with caps on tracks, events, notes and duration. Truncated, oversized and hostile files are fuzzed. | `tests/test_midi_io.py` |
| MusicXML parser: DTDs, external entities and entity expansion are refused at the expat level; compressed files have caps on member count, member size, total size and compression ratio; archive paths are never used as file paths. | `tests/test_musicxml_reader.py` |
| Audio: the container is probed before decoding; duration, channels and sample rate are capped; decoding happens in memory. | `tests/test_audio_transcription.py` |
| File type is decided from content, not from the name or the declared type. | `tests/test_workflows.py`, `tests/test_api_projects.py` |
| LilyPond input is a programming language, so no user-supplied LilyPond ever reaches it. Source is generated from numbers plus two escaped strings. The subprocess has no shell, a scrubbed environment, a private temporary directory, resource limits on POSIX, a timeout, and an output cap. | `tests/test_lilypond.py` |
| Model output is parsed strictly into an `ArrangementPlan`. The model never produces notes, so it cannot put anything on the page that the verifier has not checked. Response size, attempts, time and cost are capped. | `tests/test_agent.py`, `tests/test_engine.py` |

### Abuse and resource control

| Control | Tested in |
|---|---|
| Rate limits per address and per user, with separate budgets for sign-in, password reset, email resend, upload, arrange, account export and account deletion. Backed by the database when there is more than one instance. `X-Forwarded-For` is only trusted for the configured number of proxies. | `tests/test_api_security.py`, `tests/test_storage.py` |
| Quotas: projects, stored bytes, jobs per day, transcriptions per day, concurrent jobs. | `tests/test_api_projects.py` |
| Jobs have a wall-clock limit per kind, can be cancelled, are retried a bounded number of times after a crash, and are recovered when a worker dies. Two workers never run the same job (also run against real Postgres). Repeating a request with the same idempotency key starts one job. | `tests/test_api_projects.py`, `tests/test_postgres_integration.py` |

### Browser

| Control | Tested in |
|---|---|
| `Content-Security-Policy: default-src 'self'; script-src 'self' 'wasm-unsafe-eval'` and no inline script. `'wasm-unsafe-eval'` exists only so the notation engine can compile its WebAssembly; `eval` stays forbidden. | `tests/test_api.py`, `tests/test_browser_e2e.py` (fails on any CSP console error) |
| The frontend never assigns `innerHTML`. Every string from the server or the user is set as text. Notation SVG is parsed as a document and adopted node by node after scripts, `foreignObject` and event-handler attributes are removed. CI greps for forbidden patterns. | `.github/workflows/ci.yml`, `tests/test_api_projects.py` (a title containing HTML is stored and shown as text) |
| `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy`, a restrictive `Permissions-Policy`, and HSTS in production. | `tests/test_api.py`, `tests/test_api_security.py` |
| API responses are `no-store`. Third-party browser code is pinned by SHA-256 at fetch time and served from the same origin. | `tests/test_api_security.py`, `fetch_vendor.py` |

### Errors, logs and configuration

| Control | Tested in |
|---|---|
| Unhandled errors return a generic body with a request id. Paths, SQL and stack traces never reach the client. Job failures show a safe message; the internal detail stays in the log. | `tests/test_api_security.py`, `tests/test_api_projects.py` |
| Passwords, tokens, cookies, reset links and API keys are masked before logging. Email addresses are logged as domains only. | `tests/test_security.py`, `tests/test_email.py` |
| Production refuses to start with insecure cookies, no CSRF, wildcard or non-https origins, SQLite without an explicit override, a console email provider, a relative artifact directory, incomplete S3 credentials, the model enabled without a cost cap, or `PUBLIC_LAUNCH` without operator details. | `tests/test_settings.py` |
| `/metrics` requires a token in production. | `tests/test_api_security.py` |

### Privacy

| Control | Tested in |
|---|---|
| Account export contains every record and file, and no password hash, token hash or other user's data. | `tests/test_api_projects.py` |
| Account deletion needs the password and a typed confirmation, removes every row and every stored file, and reports how many files were removed. Asserted on SQLite and on real Postgres by counting rows afterwards. | `tests/test_api_projects.py`, `tests/test_postgres_integration.py` |
| No analytics, advertising or third-party requests. The browser test fails on any request to another origin being refused by the CSP. | `tests/test_browser_e2e.py` |

## Known limitations

These are real and should be read before a public launch.

1. **No external review.** No penetration test, no third-party audit.
2. **No multi-factor authentication** and no breached-password check. Password
   policy is length only.
3. **No account lockout.** Repeated sign-in failures are slowed by rate limits
   per address and per account, not blocked.
4. **No malware scanning of uploads.** Files are parsed by this application's
   own bounded parsers and are never executed or served back inline, but a
   stored original is returned byte for byte in the account export.
5. **The S3 adapter has not been exercised against a live bucket.** Its request
   signing is tested against the worked example in AWS's documentation, and the
   store against a fake bucket (`tests/test_artifacts.py`). Run
   `python -m arranger_api.artifacts --check` against the real bucket first.
6. **Files are not encrypted by the application.** Encryption at rest is
   whatever the database, volume or bucket provides.
7. **LilyPond and the audio decoder are large native programs.** They run with
   limits, not in a separate sandbox or container. Resource limits are not
   applied on Windows.
8. **SQLite mode is single-host.** Rate limits and job claims are correct across
   processes on one machine, not across machines. Use Postgres for more than
   one host.
9. **`style-src` allows `'unsafe-inline'`** because the notation SVG carries
   inline style attributes. Script policy is unaffected.
10. **Backups are not made by the application.** See the runbook.
11. **Dependency pinning is partial.** `requirements.lock` was generated on
    Windows, so Linux-only transitive packages are not pinned. `pip-audit` runs
    in CI on both the environment and the lock file.
12. **The API hardening layer was reviewed by its test coverage**, test by test
    against the twelve audit findings, not line by line.

## Automated scanning

The `security` CI job runs on every push and pull request:

| Scanner | What it checks | Where its findings are handled |
|---|---|---|
| Bandit (`bandit -r src -ll`) | The Python source, medium severity and above | Real findings are fixed; a false positive carries `# nosec <id>` with the reason on the same line |
| pip-audit | The installed environment and `requirements.lock` against known vulnerabilities | Upgrade the pin in the lock file |
| Gitleaks | The whole git history for committed secrets | Rotate the secret, then rewrite history if the repository is private enough for that to matter |
| OWASP ZAP baseline | The freshly built image, passively, in the Docker job | Fix in the app; accepted findings are listed with reasons in `.zap/rules.tsv` |
| Snyk | `requirements.lock`, high severity and above | Runs only when the repository has a `SNYK_TOKEN` secret |

## Pre-deploy checks

```powershell
.venv\Scripts\python tests\test_constraints.py
.venv\Scripts\python -m pytest -q
.venv\Scripts\python -m ruff check .
```

CI additionally runs the Postgres journey, `pip-audit`, gitleaks, and the image
smoke test. Do not deploy from a red `main`.

## Reporting a vulnerability

There is no published security contact yet. It belongs with the operator details
in launch configuration (`OPERATOR_CONTACT_EMAIL`); see `docs/legal-review.md`.
